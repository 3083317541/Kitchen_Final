## 1. 项目定位与硬性约束

| 项 | 内容 |
|---|---|
| 引擎 | Unity **2022.3.62f3c1**，Built-in Render Pipeline |
| 输入 | 旧版 Input Manager（`activeInputHandler: 0`） |
| UI | uGUI + TextMeshPro 3.0.7 |
| 第三方依赖 | **无**。无插件、无网络、无外部资产 |
| 视角 | 俯视角 3D（透视相机，俯角 55°，FOV 50） |
| 规模 | 52 个 C# 文件、14,601 行（运行时 41 文件 / 9,218 行，编辑器 11 文件 / 5,383 行） |

设计上刻意遵守的六条约束，它们是这个工程所有结构选择的来源：

1. **Manager 不读输入。** 只有 `InputManager` 碰 `UnityEngine.Input` 和 `EventSystem`。
2. **Manager 不随机找场景对象。** 所有依赖由 `GameRuntime` 在 `Boot()` 里显式注入。
3. **厨具没有各自的计时器。** 所有加工进度由 `WorkManager` 在一个循环里统一推进。
4. **加工规则不在 MonoBehaviour 里。** 用 ScriptableObject 策略（`CookerWorkStrategy`）按 `WorkType` 分派。
5. **所有规则不挤在一个 MonoBehaviour 里。** 按领域拆成 `Grid / Staff / Cooker / Work / Inventory / Recipe / Order / PlateReturn` 八个系统。
6. **库存只有一个入口。** 任何物品数量变化都必须经过 `InventoryManager`。

## 2. 全局架构

### 2.1 分层

```
表现层    CookerView / StaffView / GridView / PlacementPreview / Whitebox / ViewFactory
            ↑ 只被读，不下达规则
─────────────────────────────────────────────────────────────────
编排层    GameRuntime（唯一入口：初始化、注入、分派意图、定义更新顺序）
            ↓ 持有并驱动
系统层    GridManager  CookerManager  StaffManager  WorkManager
          InventoryManager  RecipeManager  OrderManager  PlateReturnManager
            ↑ 都是 GameSystem（MonoBehaviour），通过 Initialize(runtime) 拿到注入
─────────────────────────────────────────────────────────────────
输入/UI   InputManager（唯一读输入）        UIManager（唯一碰 UI）
─────────────────────────────────────────────────────────────────
数据层    8 个 ScriptableObject 类型（Level / Cooker / Item / Recipe / Order / 4 种策略）
            ↑ 数值与内容全部在这里，代码里没有硬编码的价格或时长
```

### 2.2 依赖方向

单向，从上到下：

- `GameRuntime` 认识所有系统；系统之间**互不认识**，只认识 `GameRuntime`。
- `CookerRuntime` / `StaffRuntime` 是纯 C# 对象，通过 `Owner` 反向访问 `GameRuntime`，因此能拿到 `Inventory` / `Recipes` / `Grid`，而不需要静态单例。
- `GameRuntime.Instance` 只服务于两处需要静态上下文的场景：`InputManager` 把鼠标射线翻译成格子，以及编辑器验收。系统内部不使用它。

### 2.3 八个系统的职责边界（一句话版）

| 系统 | 只负责 | 明确不负责 |
|---|---|---|
| `GridManager` | 格子是否存在、谁占用、坐标换算 | 谁该移动、能不能买 |
| `StaffManager` | 员工的创建、选中、离散移动、插值 | 加工进度 |
| `CookerManager` | 厨具的生命周期（买/放/移/拆）、占用登记 | 加工规则、配方匹配 |
| `WorkManager` | 每帧遍历厨具并驱动策略 | 具体加工细节（交给策略） |
| `InventoryManager` | 数量与预留的**唯一**读写点 | 什么算合法的配方 |
| `RecipeManager` | 配方匹配、输入锁定、原子转换 | 何时开始/结束（策略决定） |
| `OrderManager` | 订单发放、交付校验、奖励、超时 | 库存细节 |
| `PlateReturnManager` | 待归还盘子的统一队列 | 盘子从哪来 |

## 3. 启动流程

### 3.0 场景入口

```
MainMenu.unity（构建顺序 0）
  点击「开始游戏」→ CampaignProgress.Reset() → SceneManager.LoadScene("Kitchen")
      ↓
Kitchen.unity（构建顺序 1）
  按 CampaignProgress.LevelNumber 加载 "Kitchen/Level_0N" 资产
      ↓
  全部订单完成 → LevelManager 记录奖励 → 结算面板 → 「进入下一关」→ 重新加载 Kitchen
```

`CampaignProgress` 是静态类，是"当前第几关"的唯一持有者。之所以用静态而不是单例对象，是因为
菜单、厨房、结算面板分属三个场景：静态字段跨场景存活，而且不需要往场景里塞常驻对象。它**不写盘**，
关掉游戏就是从第一关重新开始。

### 3.1 时序

```
Awake()  → Boot()          // 建模、注入、造关卡
Start()  → StartLevel()    // 发第一张订单 + 刷 UI
Update() → AdvanceFrame()
```

`Boot()` 被拆出来（而非塞在 `Awake`）的唯一理由：**自动化验收需要自己决定何时启动、按多大步长推进**，所以必须有一个可被外部调用的入口。

### 3.2 `Boot()` 的六个阶段

严格按此顺序，每一步的顺序都有理由：

| # | 动作 | 为什么必须在这个位置 |
|---|---|---|
| 1 | `Time.timeScale`、找相机 | 相机是输入射线的前提，缺了世界点击全失效（会报错而不是静默失败） |
| 2 | `inputManager.Initialize(camera)` | 输入不依赖任何系统，且后续系统可能要读交互模式 |
| 3 | 八个系统 `Initialize(this)` | 注入阶段，此时不做任何世界操作 |
| 4 | `SetWorldRoots(...)`（cooker / grid / staff） | 挂载点确定后才能造视图；这里同时**删除场景里的 Preview 预览对象** |
| 5 | `plateReturn.Configure(10, 20)` | 盘子归还区间来自 `GameRuntime` 的 Inspector 字段 |
| 6 | `WhiteboxMaterialLibrary.Load()` | 材质资产在造 prefab 之前要就位，否则 prefab 里的材质引用会是空 |
| 7 | `ResolveLevelConfig()` → `ApplyLevelContent()` | 关卡可能为空，回退到代码内置内容；然后向 recipe / cooker / order 三个系统下发目录，并缓存干净盘子/脏盘子 |
| 8 | `BuildWorld()` | 造网格可见物（格线、高亮） |
| 9 | `grid.BuildGrid(level)` | 建格子字典（`CellCount == 0` 会明确报错） |
| 10 | `inventory.ApplyStartingInventory()` | 初始库存 |
| 11 | `cooker.SpawnLevelCookers()` / `staff.SpawnLevelStaff()` | 造关卡自带对象 |
| 12 | `grid.RebuildOccupancyFromManagers()` | **补登记**：格子先建成空的，两个 Manager 造对象时各自登记，这里做一次全量对账 |
| 13 | `ui.Initialize()` + `BindInput()` | UI 最后初始化，因为它读的所有数据此时才齐 |
| 14 | `Money = level.StartingMoney` | UI 初始化后才能安全刷新 |
| 15 | 订阅五个输入意图事件 | — |
| 16 | `initialized = true` + 一条通知 | 未初始化时 `AdvanceFrame` 直接返回，避免半初始化状态被 tick |

### 3.3 关卡解析的三级回退

```
Inspector 的 levelConfig
  ↓ 空
Resources.Load<LevelConfig>("Kitchen/Level_01")
  ↓ 空
GameContentFactory.CreateRuntimeContent()   // 纯代码生成，保证场景永远能玩
```

这条链保证了「场景拖进一个空对象也能跑」，代价是代码里保留了一份默认内容工厂。

## 4. 帧循环

### 4.1 `AdvanceFrame(unscaledDeltaTime, timeScale)`

这是**唯一**定义更新顺序的地方。`Update()` 只是 `AdvanceFrame(Time.deltaTime, 1f)`。

```
ElapsedTime += dt

1. input.Tick(dt)              // 采样一次输入，翻译成意图事件
2. work.Tick(dt)               // 推进所有厨具加工
3. plateReturn.Tick(dt)        // 盘子归还
4. order.Tick(dt)              // 订单计时
5. staff.Tick(dt)              // 员工插值移动（更新世界坐标）
6. cooker.Tick(dt)             // 从网格刷新"是否被员工激活"
7. ui.Tick(dt)                 // 节流刷新 UI
```

### 4.2 两处顺序不是随意的

**(a) 输入在最前。** 玩家这一帧的点击要在同一帧被处理，否则点击反馈会晚一帧，按住方向键连续移动也会感觉黏。

**(b) `staff` 在 `cooker` 之前。** `cooker.Tick` 重新读取「该格子上有没有员工」来决定是否激活。如果反过来，员工刚走进厨具格的**这一帧**厨具仍会被判为未激活，玩家会感到"走上去要等一下才开始"。现在的顺序让激活在同一帧生效。

注意 `staff.Tick` 只做视觉插值：**离散格子位置在按键的瞬间就更新了**（`TryMove` 里直接改 `GridPosition` 并登记占用），所以「谁站在哪一格」是即时可信的，模型走过去只是表现。

### 4.3 为什么 `AdvanceFrame` 是 public

因为它接受 `unscaledDeltaTime` 和 `timeScale`，验收程序可以用固定步长（例如一次推进 0.05 秒）跑完 10 秒的煎制过程，而不依赖真实帧率。这让「5 秒煎好」这类规则可以**确定性地**被验证，而不是"等一会儿看看"。

## 6. 网格系统

### 6.1 坐标数学（`KitchenGridMath`）

抽成一个**普通 struct**，是为了让编辑器预览和运行时用**同一套**换算，避免"Scene 里摆的位置和 Play 起来不一样"。

```
OriginX = mapCenter.x - width  * cellSize * 0.5 + cellSize * 0.5
OriginZ = mapCenter.z - height * cellSize * 0.5 + cellSize * 0.5
GroundY = groundHeight + mapCenter.y

GridToWorld(cell)  = (OriginX + cell.x * cellSize, GroundY, OriginZ + cell.y * cellSize)
WorldToGrid(world) = (Round((world.x - OriginX) / cellSize),
                      Round((world.z - OriginZ) / cellSize))
CentreCell         = (width / 2, height / 2)
```

那个 `+ cellSize * 0.5` 是关键：它让**整个地图以 `mapCenter` 为中心**，而不是以某个角为中心。这样 5×5 和 6×6 都能正确居中（奇数尺寸会有一个正中间的格子，偶数尺寸则中心落在四格交界，公式对两种都成立）。

### 6.2 占用模型

```
cells : Dictionary<Vector2Int, GridData>
GridData { cookerId, staffId, staffIds(List) }
```

- **一个格子最多一台厨具**，由 `cookerId` 唯一确定。
- **一个格子最多一名员工**，由 `staffId` 唯一确定。
- **员工与厨具可以共格** —— 这不是疏忽，是这个游戏的核心机制：员工站到厨具格上就等于"激活"它。
- 因此有两套独立的占位判定：`IsFreeForCooker(cell, ignoreId)` 只看 `cookerId`；`IsFreeForStaff(cell, staffId)` 只看 `staffId`。

### 6.3 关键不变量：网格是唯一真相

`CookerManager` 和 `StaffManager` 各自持有运行时列表，但「谁在哪一格」永远以 `GridManager` 为准。`RebuildOccupancyFromManagers()` 在启动末尾做一次全量对账，`ValidateConsistency()` 可以随时校验两边是否一致（验收里就有一项专门跑它）。

`TryMoveCookerTraced()` 会返回最后一步的失败原因（`LastMoveTrace`），这样 UI 能告诉玩家"为什么不行"，而不是只返回 false。

## 7. 八个系统详解

### 7.1 员工（`StaffManager` + `StaffRuntime`）

**创建**：按 `level.StaffCount` 循环，优先用 `StaffSpawnOffsets` 指定的偏移（相对中心格），被占了就 `TryFindNearestFreeCellForStaff` 找最近的空格。

**移动**：`TryMove(runtime, direction)` 的校验顺序是

1. 方向必须是四邻之一（`|dx| + |dy| == 1`）—— 本版本**不做寻路**
2. 目标在界内
3. 目标格没有别的员工
4. 登记到网格（`TryMoveStaff`）

任一失败都会 `Notify` 一句中文原因。成功时：

```csharp
runtime.GridPosition       = target;   // 逻辑位置立刻生效
runtime.TargetGridPosition = target;
runtime.IsMoving           = true;     // 视觉开始插值
```

**`Tick` 里只做视觉插值**：

```csharp
Vector3 flatTarget = new Vector3(target.x, current.y, target.z);  // 高度保持
Vector3 next = Vector3.MoveTowards(current, flatTarget, speed * dt);
if (到达) { next = flatTarget; IsMoving = false; }
```

`MoveTowards` 而非 `Lerp` 是有意的：`Lerp` 每帧按比例逼近，速度会随距离变化且永远到不了终点；`MoveTowards` 是恒定速度且在 `speed * dt >= distance` 时**精确落点**，所以用 `sqrMagnitude <= 1e-6` 判终点是可靠的。

员工移动**不打断上一步**（`IsMoving` 时仍可再次 `TryMove`），所以按住 WASD 手感是连续的。

### 7.2 厨具（`CookerManager` + `CookerRuntime`）

**生命周期**：`CreateCooker(definition, cell, free)` → `SetPlacement` → `cookers.Add` → `CreateView`。

**扣款顺序是刻意的**：

```
TryBuildCooker(...)
  ├─ 界内？  ├─ 格子空？  ├─ 钱够？
  └─→ CreateCooker(..., free: false)
        ├─ 再校验一次（防止状态在两步之间变了）
        ├─ SpendMoney
        ├─ TryOccupyCooker ── 失败则 AddMoney 退款
        └─ 造视图
```

**先校验后扣款、扣款后若占位失败立即退款**，是为了保证「不会出现钱扣了但厨具没出来」的半成品状态。

**激活**：`Tick` 里每帧重新读网格：

```csharp
int staffId = Grid.GetStaffId(cooker.GridPosition);
bool active = staffId > 0;
if (active != cooker.IsActive) { cooker.IsActive = active; View.SetActiveState(active); }
```

每帧从网格重算，而不是维护"员工进入/离开"事件，意味着**不可能出现厨具在员工走开后继续工作**的状态泄漏。代价是每帧一次字典查找，对这个规模完全可以接受。

**移动**：成功后显式把 `IsActive = false; ActiveStaffId = -1;`，让新位置上的员工在下一帧重新激活它。

**拆除**：先 `Release(Slots)` 把预留材料还给库存，再 `ForgetLock()`，再把产出收进库存，最后释放网格并销毁视图。**拆除不退款**（`TryRemoveCooker` 不减价），这是一条明确的玩法取舍，写在已知限制里。

### 7.3 加工（`WorkManager` + 四种策略）

**`WorkManager.Tick` 是唯一的推进循环**：

```csharp
foreach (cooker in cookers) {
    strategy = GetStrategy(cooker.Definition.WorkType);   // 字典查找，无 if/else 链
    if (!cooker.IsActive) {
        strategy.OnDeactivated(cooker);                   // 完全不推进
        cooker.StatusText = 有产出 ? "已完成，请收取产出" : "空闲（需要员工）";
        continue;
    }
    strategy.Tick(cooker, dt);
}
```

**关键点**：厨具未激活时**根本不会调用 `strategy.Tick`**，因此 `WorkSeconds` / `WorkTicks` 不会被修改 —— 这就是"进度冻结、回来继续"的实现方式，不需要任何保存/恢复逻辑。

策略从 `WorkStrategyHolder`（挂在同一个 `GameObject` 上的组件）读取，这仍然满足"不搜索场景"：组件读取**自己所在对象**上的其他组件是允许的。

**四种策略的算法**

| 策略 | 算法 | 产出归属 |
|---|---|---|
| `ChoppingWorkStrategy` | 累加 `WorkSeconds`，`while (WorkSeconds >= interval && WorkTicks < required)` 逐刀扣减计数；够数后转换 | 留在厨具输出槽（`AddOutput`），需要玩家收取 |
| `TimedWorkStrategy`（基类 `RepeatingConversionStrategy`） | 累加 `WorkSeconds`，达到 `Definition.Duration` 即转换 | 同上 |
| `AssemblyWorkStrategy` | 同基类，但 `TryBeginUnit` 换成"逐次补料直到凑满整份配方" | 同上 |
| `WashingWorkStrategy` | 同 `Timed`，但 `ProduceOutput` **被覆写为空** | 直接进共享库存 |

**为什么洗碗台要覆写 `ProduceOutput`**：如果干净盘子留在洗碗台的输出槽里，它就会因为"输出槽非空"而拒绝洗下一个脏盘子，玩家必须每洗一个就手动点一次收取。让产出直接进库存，洗碗台才能连续工作——这符合"洗碗台是流水线工位"的直觉。

那个 `while` 循环带 `guard < 100000` 上限，是为了防止 `interval` 被配成极小值时死循环。

**`CookerWorkHelpers` 的两个锁**：

- `TryLockSingleRecipe` —— 煎锅/洗碗台用。`HasAnyOutput` 时返回 false（输出槽满了就不开工），然后找最高优先级可用配方，一次性预留全部输入。
- `TryLockAssemblyRecipe` —— 组装台用。它在**已有预留**的基础上，找"再补几个就能凑满"的配方，允许玩家把四种材料一个一个送进去。

### 7.4 库存（`InventoryManager`）

**为什么需要"预留"（reservation）**：假设两个煎锅同时看到"生肉片 1"，如果只检查 `总数 >= 1`，两个都会开工，最后其中一个的材料凭空消失。所以库存分两个计数：

```
totals[item]       // 总持有
reservations[item] // 已被某台厨具预定
Available = max(0, totals - reservations)   // 只有这个能被动用
```

**API 语义表**（很容易用错，这里写清楚）：

| 方法 | 语义 | 失败时 |
|---|---|---|
| `Has(item, n)` | `Available >= n` | — |
| `TryReserve(item, n)` | 从可用里划走 n，总数不变 | 可用不足则返回 false，不做任何改动 |
| `Release(item, n)` | 把 n 从预留里退回可用 | 安全，幂等 |
| `TryConsume(item, n)` | 直接减少总数（必须**未被预留**） | 可用不足则 false |
| `TryConsumeReserved(item, n)` | 同时减少预留和总数（消耗已预定的） | 预留不足则 false |

**这里曾经有一个真实 bug**：转换完成时用 `HasAll(recipe.Inputs)` 检查材料，但输入早已被预留，`Has` 看的是**可用**数量（已扣掉预留），所以永远返回 false，加工永远不完成。修复方式是引入 `CanConsumeReserved()` + `TryConsumeReserved()` —— 对**已经在飞的转换**，唯一正确的检查是"预留够不够"，而不是"可用够不够"。

### 7.5 配方（`RecipeManager`）

**匹配**：`FindUsableRecipe(kind)` 遍历该厨具类型的配方，返回第一个 `HasIngredients()` 为真的。

**排序**：`ApplyLevel` 里按 `Priority` **降序**排序（`b.CompareTo(a)`），所以数值大的先被选中。`assemble_meat_bread` 的优先级 10 高于 `assemble_salad` 的 0，就是为了让"四材料套餐"先于"两材料沙拉"被匹配，否则组装台会永远先做沙拉。

> 注意：`RecipeDefinition.priority` 的 `[Tooltip]` 写的是"Lower values are evaluated first"，与实际行为（降序，高值优先）**矛盾**。这是一处待修的文档错误，实际生效的是**高值优先**。

**原子转换 `TryConvert(cooker, recipe, consumeReserved, out produced)`** —— 整个工程唯一创建成品的地方，顺序很关键：

```
1. 若 consumeReserved：先 CanConsumeReserved() 预检      ← 预检失败直接返回，不动任何东西
2. 逐个 output 加进库存，收集到 produced 列表
3. 若一个 output 都没产出 → 中止（不消费输入）
4. 逐个 input 消费（reserved 用 TryConsumeReserved，否则 TryConsume）
5. producedStacks = produced
```

**"先产出、后消费"** 是刻意顺序：即使中途出现异常，结果也是"材料还在、产物多出"，而不是"材料没了、产物也没有"。前者玩家会看到多余的东西（明显、可修），后者是静默的资源丢失（难发现）。

**`MatchesReservedExactly`** 用于组装台：预留的每一种材料数量必须**精确等于**配方要求，且槽里不能有配方外的物品。这条保证了"多送一份番茄就不算沙拉"。

### 7.6 订单（`OrderManager`）

**状态机**：`Active → Completed | Failed`，每次结算后立刻 `IssueNextOrder()`（序列循环，用取模）。

**交付校验顺序**（全部通过才动库存）：

```
1. current != null ?
2. IsActive ?          已结算则明确告诉玩家"已完成/失败"
3. TimeRemaining > 0 ? 已超时则转 Fail 并返回
4. dish/plate 定义存在 ?
5. 库存 Has(dish, needed) ?
6. 库存 Has(cleanPlate, needed) ?
7. 消费（TryConsume × 2）
8. 加钱、completedOrders++、为每个盘子入队归还
9. OrderSettled 事件、发下一张
```

**奖励只结算一次**的保证来自第 2 步：结算后 `State` 立刻离开 `Active`，重复点击只会得到提示，不会重复加钱。

### 7.7 盘子循环（`PlateReturnManager`）

上菜时每个盘子 `EnqueueReturn()`，入队的是一个**随机 10–20 秒的延迟**（`Queue<float>`）。

```
Tick:
  if 队列空 → nextReturnIn = -1, return
  if nextReturnIn < 0 → nextReturnIn = peek()        // 队首到期时间
  nextReturnIn -= dt
  if nextReturnIn > 0 → return
  dequeue() → 库存 +1 脏盘子 → 通知玩家
  nextReturnIn = 队列还有 ? peek() : -1
```

**所有盘子共用一个队列和一个计时器**，严格按入队顺序归还。没有任何盘子拥有独立计时器，也没有每盘一个 coroutine —— 这正是约束 3 的体现。

### 7.8 输入（`InputManager`）

**唯一读输入的地方**。它做三件事：

1. **维护交互模式**：`Normal / Build / SelectIngredient / MoveCooker`（`InteractionMode` 枚举共四个值；"移动员工"复用 `MoveCooker` 模式的按键处理，不单独占一个模式）
2. **采样命中**：鼠标射线打 `groundMask` 得到格子，打 `interactableMask` 得到可选中对象
3. **把输入翻译成意图，通过事件抛出**（`BuildRequested`、`MoveStaffRequested`、`CookerContextRequested` …）

**UI 永远优先**：`PointerOverUI` 为真时，世界输入整帧被忽略。

```csharp
PointerOverUI = EventSystem.current != null &&
                EventSystem.current.IsPointerOverGameObject();
```

这条是"点按钮不会顺手在按钮下面的空地上买了一台厨具"的保证。验收里有两项专门测它（`ui_blocks_world_input`、`ui_suppresses_ground_hover`）。

**键盘连发**：`moveRepeatDelay = 0.22` 秒，首次按下立即触发，之后按住按间隔重复。四个方向各自记录"上一次方向"，避免换方向时被旧的重复计时挡住。

### 7.9 UI（`UIManager`）

**唯一碰 UI 的地方**。Manager 不引用任何 `Text` / `Button`，只调用 `Runtime.Notify(...)`；`UIManager` 订阅 `MessageRaised` 显示到通知面板。

**节流刷新**：`refreshInterval = 0.2` 秒。每帧刷新会不停产生临时字符串（GC 压力），而 5Hz 对玩家已经完全够用。`Tick` 里：

```csharp
refreshTimer -= dt;
if (refreshTimer <= 0) { refreshTimer = refreshInterval; RefreshValues(); }
```

**面板**（6 个）：`TopBar`、`OrderPanel`、`CookerShopPanel`、`SelectionPanel`、`RecipeProgressPanel`、`NotificationPanel`。

**绑定方式是按名字查找子物体**（`KitchenUIBuilder.WireUI`）。好处是换成美术做的 Canvas prefab 时，只要子物体命名一致就能自动接上，不需要改代码。

### 7.10 关卡与战役（`LevelConfig` + `LevelManager` + `OrderManager`）

三关的差异全部在数据里，代码不写死任何一关：

| 关卡 | 金钱 | 员工 | 预放厨具 | 厨具目录 | 订单 |
|---|---|---|---|---|---|
| L1 沙拉 | 170（正好 = 50 + 120） | 1 | 无（摆放就是教学内容） | 切菜台、组装台 | 沙拉、沙拉加急 |
| L2 沙拉与汉堡 | 250 | 2 | 煎锅 | 切菜台、煎锅、组装台 | 沙拉加急、汉堡 |
| L3 盘子循环 | 300 | 3 | 煎锅、洗碗台 | 全部四台 | 沙拉加急、汉堡 ×2 |

**内容收敛（`ResolveContent`）**：一关"有哪些物品、能用哪些配方"不是手写的，而是算出来的 ——
从初始库存和订单菜品出发，反复应用"所有输入都齐备的配方"把产物并入物品集，直到不再变化，再据此
保留配方。

这个顺序很关键。早期实现是"先按配方过滤、再从幸存配方补物品"，但物品集一开始没有产物，所有配方
都被滤掉，补物品的循环于是无事可做 —— 结果 **L1/L2 的配方表是空的**（磁盘核对：`recipes: []`），
游戏做不出任何菜。改成从库存正向推导后：L1 得 3 条（切包菜、切番茄、组装沙拉），L2 得 9 条，
L3 得 10 条（多一条洗盘子）。

**订单清单有限**：`IssueNextOrder` 不再取模循环，走到末尾就 `Current = null` 并触发一次
`LevelCleared`。**失败不推进游标**，而是重发同一张，所以失误不会让关卡变得无法通过。

**奖励不叠加**：`ApplyClearReward` 只记录奖励用于展示，不会在下一关的钱和员工上再加一遍 ——
下一关的内容由它自己的 `LevelConfig` 决定，避免两处重复计算。

**验收用的是沙箱关卡**（`Level_Sandbox.asset`）：4 台厨具已就位、3 名员工、全部物品与配方。
验收要测的是系统行为，不是关卡平衡，所以不能让 L1 的"只有 1 名员工"去影响测试。

> 注意：场景里的 `Preview` 预览按 **Level_01** 生成，而 L1 没有预放厨具，所以 Scene 视图里看不到
> 厨具 —— 这符合设计（摆放是教学内容）。调厨具外观直接改 `Prefabs/Cookers/*.prefab` 即可，与关卡无关。

## 8. 视图层与美术接缝

### 8.1 `ViewFactory` 的优先级链

```
CreateCookerView(definition)
  ├─ definition.ViewPrefab != null ?  → Instantiate(prefab) → 确保有 CookerView → Configure
  └─ 否则                              → BuildWhiteboxCookerView(definition)   // 图元白模
```

**关键设计**：白模和 prefab **由同一段代码产生**（`KitchenPrefabGenerator` 就是调用 `BuildWhiteboxCookerView` 再把结果存成 prefab）。所以两条路径做出来的东西不可能不一致，这也是为什么"改 prefab"不会和"回退白模"打架。

### 8.2 场景预览与运行时

场景里保存的可见模型挂在 `<Root>/Preview` 容器下，由 `KitchenScenePreview` 用 `PrefabUtility.InstantiatePrefab` 生成，**保留 prefab 连接**，所以改 prefab 会立刻反映到 Scene 视图。

运行时启动时，`CookerManager.SetWorldRoots` 和 `StaffManager.SetWorldRoots` 会**删掉这个 `Preview` 容器**，然后自己造视图。所以不会出现"预览 + 运行时两套模型"的重复。

### 8.3 材质（这里踩过一个坑，值得记录）

白模材质最初是用 `new Material(...)` + `HideFlags.DontSave` 在内存里创建的。**这种材质不是资产，存进 prefab 时引用被序列化成 `null`**：

```
m_Materials:
  - {fileID: 0}     ← prefab 里的真实内容
```

结果所有实例化出来的厨具和员工都渲染成 Unity 的洋红色 missing-material 错误着色器。

修复分三层：

1. **材质写成资产**：`KitchenMaterialGenerator` 在 `Assets/_Game/Art/Materials/` 生成 `.mat`，并汇总成 `Resources/Kitchen/WhiteboxMaterials.asset`（`WhiteboxMaterialLibrary`）。
2. **`Whitebox` 按名字从库取材质**：`MaterialName(prefix, color)` 生成稳定名字，生成器和运行时用同一个函数算名字，所以一定对上。
3. **保存 prefab 时显式写回材质**：`KitchenPrefabGenerator.SavePrefab` 先用**层级路径**记录每个渲染器该用什么材质，存成 prefab 后再按路径写回；不是资产的材质用 `AssetDatabase.AddObjectToAsset` 嵌入 prefab。另加 `WarnAboutMissingMaterials` 在日志里直接报"哪个 prefab 有几个渲染器没材质"。

### 8.4 层级与拾取

`GameLayers` 定义三层：`Ground`（地面/格子，射线打这里算格子）、`Interactable`（厨具/员工，可点选）、`UI`。`Whitebox` 造每个零件时递归设置层，所以美术换模型后只要挂在正确的父节点下就会继承正确层。

### 8.5 视图组件的容错（另一处值得记录的设计）

`CookerView` / `StaffView` 的内部引用（`visualRoot`、`modelRoot`）是**非序列化字段**。Prefab 实例化后这些字段是 `null`，即使 prefab 里已经有完整模型 —— 于是 `EnsureBuilt()` 会再建一套，导致模型重复（一次真实的 bug：所有零件都出现两份）。

修复：`EnsureBuilt` 先按名字找**已存在的**容器（`transform.Find("Visual")`），找到就接管，而不是重建。这个模式叫"adopt existing"，是 prefab 化视图的标准解法。

## 9. 编辑器工具链

都是菜单 **`Kitchen/...`** 下的命令。生成顺序是有依赖的：

```
1. 数据资产   KitchenDataAssetGenerator   → Assets/_Game/Data/**.asset
2. 材质资产   KitchenMaterialGenerator    → Art/Materials/*.mat + Resources/.../WhiteboxMaterials.asset
3. 美术 prefab KitchenPrefabGenerator     → Prefabs/{Cookers,Staff,Grid,Ingredients}/*.prefab
4. 场景       KitchenSceneBuilder         → Kitchen.unity（含预览）
5. UI         KitchenUIBuilder            → Canvas 的 6 个面板
6. 中文字体   KitchenSceneGenerator.EnsureFontAsset → Art/Fonts/KitchenHudCJK.asset
```

**为什么材质必须在 prefab 之前**：prefab 会序列化材质引用；材质不存在时序列化成 null（就是上面那个洋红 bug）。

**为什么 prefab 必须在场景之前**：场景预览用 `InstantiatePrefab` 实例化它们并保持连接。

**场景生成里两个必须做对的点**：

- `EditorSceneManager.NewScene(...)` **会让上一个场景持有的资产引用失效**。原先相机取景拿到的 `level` 变 null，导致相机从不框景。修复是 `NewScene` 之后**重新解析** level 和 font。
- TMP 的 `Awake` 在 `AddComponent` 时就解析字体，早于我们 `text.font = ...` 的赋值。所以必须在 Canvas 建好之后，直接写序列化字段 `m_fontAsset` 强刷（`ApplyFontToAllLabels`）。

**字体**：中文字体图集从系统字体（微软雅黑 / Noto Sans SC / SimHei）动态生成。`Font.CreateDynamicFontFromOSFont` 交给 TMP 的 `CreateFontAsset` 会返回 null，**必须加载真实的字体文件资产**才能得到可用的动态图集。

## 11. 关键不变量

这些性质在代码里被刻意保住，改动时不要破坏：

| # | 不变量 | 由谁保证 |

| 1 | 物品数量只经 `InventoryManager` 变化 | 所有库存写操作都封在该类 |

## 14. 扩展指南

### 加一种厨具

1. `CookerKind` 枚举加一项（`Scripts/Common/GameEnums.cs`）。
2. 需要新加工方式就在 `WorkType` 加一项，并写一个继承 `CookerWorkStrategy`（或 `RepeatingConversionStrategy`）的 ScriptableObject。
3. `GameContentFactory` 里加 `CookerDefinition`。
4. `Whitebox` / `CookerView` 里加白模外观（可选，不加就用通用白模）。
5. 跑 `Kitchen/3. Generate Everything`。

### 加一个配方

1. `GameContentFactory.CreateRecipes` 里加一条 `RecipeDefinition.Create(...)`。
2. 需要的话调 `priority`（数值大的先匹配）。
3. 重新生成数据资产。

### 加一种物品

1. `Ids` 加常量，`ItemDefinition` 加进 `CreateItems`，指定 `Category`。
2. 配方里引用它。
3. 重新生成（会自动生成 `Prefabs/Ingredients/Item_<id>.prefab`）。

### 换美术

见 [说明书_UI_数值_Prefab.md](说明书_UI_数值_Prefab.md) 第 3 节。核心两步：改 `Prefabs/**.prefab`，或把自己的 prefab 赋给 `Data/**/*.asset` 的 `View Prefab` 字段。

### 换 UI

面板结构在 `KitchenUIBuilder`（布局与配色），文案刷新在 `UIManager`。要换成美术做的 Canvas prefab 时，只要子物体命名与现有层级一致，`WireUI` 会按名字自动接上。

## 15. 一句话总结

这个工程的核心思路是：**把"规则"和"状态"分开放** —— 规则在 ScriptableObject 里（数据 + 策略），状态在 `*Runtime` 普通 C# 对象里，编排在 `GameRuntime` 一个地方，输入和 UI 各自只有唯一入口。所有"永不发生"的坏情况（重复消费、丢材料、离开后继续工作）都由一个明确的不变量 + 一处实现来兜住，而不是靠到处加判断。
